# 问题澄清与定义

帮助用户明确“谁、在什么场景、完成什么任务、卡在哪里、现在怎么办”，形成能继续验证的问题定义。先共同思考，用户确定关键判断后再整理文档。定义清楚与需求已验证分别记录。

## 进入任务

可以从一句话开始，不要求用户先填表。先读已有资料，复用已确定的信息。区分目标、现象、问题表达和候选方案；不要把“需要某个功能”当作问题本身。

- 只有想法或方案：先还原它想改变的用户任务与结果。
- 有反馈或记录：优先还原最近一次具体经历及实际动作。
- 已有完整定义：直接检查依据和缺口，不重走固定问答。
- 只有指标异常：将其作为现象，原因保留为假设，不编造用户或行为。

## 澄清方法

1. 复述当前理解，区分已有依据、推断和未知。多种解释会改变问题对象或范围时，说明差别，让用户决定。
2. 还原场景：谁、何时何地、在做什么、卡在哪、现在怎么凑合。场景记录与判断相关的触发条件，不为字段齐全追问无关时间或地点。
3. 分开问题与方案：听到功能名时，追问“有了它，你想解决什么？”保留原始提案为候选方案，问题表述不将指定功能当作唯一解。
4. 逐层追问为什么，对照用户做过的事，停在本次能够采取行动的一层。已有材料能回答的问题不重复问；无法确定的深层原因保留未知。
5. 明确现有办法的限制及代价。数字要有来源与口径；没有频次、损失或收益数据时，使用有依据的定性描述或标记待核查。
6. 给出候选问题定义、关键依据和最影响判断的缺口。证据矛盾、原始提案依据不足、现有办法可能足够或范围过大时直接指出，提出补证据、缩范围或重定义的建议。

每轮只追问会改变当前判断的少量问题；不要重复已回答内容，不将固定问题清单一次全部交给用户。用户陈述保留来源，不自动认定为已验证行为；单条反馈不代表整个人群，相关现象不证明因果。

## AI 适用性：沿用课件要求

讨论是否采用 AI 时，同时核查下列三项，并给出每项依据与“满足／不满足／待验证”状态：

| 条件 | 要查清什么 |
| --- | --- |
| 重复性高 | 是否反复发生或多人重复完成同类任务 |
| 标准化程度高 | 是否能够说清什么结果算好，以及判断依据 |
| 人力瓶颈明显 | 是否有人不够、成本高或排队等待等已有依据 |

三项同时满足，才可以建议采用 AI；任一项不满足，不建议按当前条件采用 AI；任一项未知，不给肯定结论，先指出验证缺口。不要擅自为创作、探索或其他产品类型增加例外。

三项满足后仍需问“改流程，能不能更便宜？”结合已有信息比较流程改进、规则或现有工具等办法；没有比较依据时标记待验证。通过三条件不等于已经证明 AI 是最优解，也不等于正式立项。技术可行性、模型选择与详细成本测算留给对应后续工作。

## 确认与撰写

讨论中可以展示候选定义，但不将未确定的对象、场景或范围标为已确认。用户的明确自然语言确认有效，已确认决定直接复用；同意定义不等于证据证明需求成立，也不自动表示同意某个 AI 方案。

用户确定关键判断后，依据[问题定义卡](references/problem-card.md)整理文档。用户明确要求先整理已有材料时，可以输出标明未知的草稿。只要求讨论时保持讨论；保存位置优先采用用户指定路径或当前项目既有文档位置，不因套用模板新建无关项目或目录。

## 完成与衔接

- 问题定义说明具体用户、任务、场景与卡点，并与候选方案分开。
- 现有办法及代价可追溯到输入，事实、推断与未知能够区分。
- 分别记录用户是否确认定义、需求是否有足够验证证据、AI 三条件是否成立。
- 下一步针对一个具体未知说明需要什么证据及如何获取，不只写“进一步调研”。

本项不执行完整画像、访谈研究、需求排序、立项、原型或 PRD。传递已确定的问题、依据和待验证假设即可；后续 Skill 不存在或未接入时，用工作职责说明下一步，不声称已经调用或完成。
