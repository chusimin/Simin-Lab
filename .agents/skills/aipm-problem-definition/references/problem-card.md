# 问题定义卡

用户确定问题对象、场景与范围后使用本结构；用户要求先整理时可生成草稿。字段按材料裁剪，重要缺口明确标出，不用空洞结论填满表格。

| 字段 | 内容 |
| --- | --- |
| 原始输入与来源 | 原话、提案或异常现象；对应文档、记录或用户陈述 |
| 谁 | 当前关注的具体用户类型；尚未确定则标记候选 |
| 什么场景 | 任务触发条件与相关环境 |
| 要完成什么 | 用户想得到的结果 |
| 卡在哪里 | 具体障碍，与候选功能方案分开 |
| 现在怎么办 | 实际处理方式及其限制 |
| 造成什么代价 | 有依据的时间、错误、损失或等待等影响；数字附来源和口径 |
| 一句话定义 | 用户、场景、任务、障碍、现有办法及仍存在的代价；不强行补齐未知信息 |
| 候选方案 | 保留用户已提出的方案，标明是否确定 |
| 证据与缺口 | 已有依据、分析推断、待验证假设及材料冲突 |
| 确认与验证状态 | 分别记录定义是否由用户确认、需求是否有验证证据 |
| 下一步 | 最关键的未知、需要的证据与建议获取方式 |

一句话可以使用“某类用户在某场景完成某任务时，遇到某障碍，目前通过某办法应对，但仍有某代价”，按实际信息改写，不机械套句式。

如讨论了 AI，增加单独一节，分别列出重复性、标准化程度、人力瓶颈的状态与依据，以及流程改进等替代办法的比较。三项全部满足才可以建议采用 AI；缺条件或缺证据时明确写出不建议或待验证，不混入用户已确认的定义。

定义确认、需求验证和 AI 方案确认不是同一状态。用户确认定义但缺少行为记录时，同时记录“定义已确认”和“需求待验证”；不要自行补写受访者、测试结果、频次或预计收益。
