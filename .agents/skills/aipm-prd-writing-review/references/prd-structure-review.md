# PRD 八块结构与审查

撰写或审查时使用。保留课件八块，按本版任务裁剪具体内容；已定判断直接复用，先整理的草稿保留未定项，不要求每块都有新信息。

| 课件结构 | 内容与检查重点 |
| --- | --- |
| 文档信息与前提 | 版本、立项依据、负责人及来源；缺失信息不补造 |
| 产品概述 | 首版待验证假设；已有产品说明本版目标和变化 |
| 版本范围 | 必须、不做、以后，承接用户已确定取舍，与功能和原型一致 |
| 角色和权限 | 按实际关系说明能用、能看、不能做，不凑角色或默认权限 |
| 场景和流程 | 相关正常、异常、转人路径的触发、行为和结束／继续状态 |
| 功能需求 | 前提、操作、规则、兜底、验收；范围与行为能对应 |
| AI 能力需求 | 做什么、做多好、谁兜；必要输入输出和限制，已定与待定、预期与实测分开 |
| 指标与非功能 | 当前任务相关的性能、安全、隐私要求、口径及依据，未知保持待定 |

审查意见定位具体问题，说明影响实现、验收或目标的原因，给出可直接修订的文字建议或需要用户判断的候选处理。文件修改遵从本次授权，不通过审查重新决定产品范围。

核查排除项是否混入功能、权限是否支持操作、异常处理是否符合规则、AI 要求是否与流程一致、验收是否有观察口径。没有依据的阈值、错误级别、数据或能力不得填入正式承诺。

课件案例的异常表只帮助理解具体程度，业务工作流、数字、安全等级和处置规则不复制为通用要求。专项评测引用已定方案，不凭表格编造测试事实。

区分已确认要求、拟议内容、来源缺口、技术确认、实际测试与用户验收。重要缺口阻止开工时指出恢复条件；PRD 或审查完成不等于产品已实现或已验收。
