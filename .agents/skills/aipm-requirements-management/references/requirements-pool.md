# 需求池输出说明

优先更新已有需求池；无维护源时先拟可审阅的候选结构，不预设工具。可用一份文档或现有表格承载，不强制生成多文件。

## 六项主字段

| 字段 | 要求 |
| --- | --- |
| 能力项名称 | 清楚表达候选动作，尚未选定方案时标候选 |
| 业务痛点和目标 | 区分当前用户问题与希望改变的结果，保留对应对象、场景与依据 |
| 建设方向 | 增长、转化、留存、体验；缺依据时待确定，不硬填 |
| 需求来源 | 业务提需或产品自驱；具体原话、材料出处与提出方另保留 |
| 当前状态 | 依据实际资料记录立项、调研、设计、开发、测试、已上线、迭代、下线或现有项目口径；未知标待核实 |
| 需求描述 | 已有说明或 PRD 的真实链接；尚未形成则如实记录 |

编号沿用现有池规则；按管理需要补提出方、原始材料出处、对象与场景、关键依据、未知、用户决定和更新理由。预计上线只写已确定的计划。

## 入池与合并记录

说明候选动作怎样对应问题、为何重要及其依据，分别记录候选、正式入池、研究验证、立项和排期。定性依据可用，无数值不补造收益、评分或数量。

合并建议展示新旧条目的共同点、差异与全部相关来源。相似名称、同一问题或多条重复反馈不自动选定解决方案；保留用户已确定的入池和合并决定。

## 内容与状态更新

说明新增、更新、保留候选与待核实项，按实际进度与资料维护。立项需有相应决定，已上线需有实际进展；文档存在和计划日期不代替完成证据。

课件状态是阶段参考，不是所有项目必须走完的单向流程。保留现有状态含义，口径不同时说明对应关系；暂不处理不等于下线，状态未知不默认放进调研。

更新保留有效编号、来源与问题，必要时补变更理由。不为了表格整齐抹除原记录、虚构 PRD 链接或填上线日期。

## 交接

向优先级与版本范围交付问题、候选动作、重要性依据、状态和未定项，保持未排序。向 PRD 工作交付已确定内容与真实链接，不在此处生成完整规格或承诺交付。
