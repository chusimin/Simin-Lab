# 需求整理与管理

先帮助用户梳理材料、候选动作与重要性，由用户确定入池和合并等关键判断，再整理或更新需求池。候选、入池、验证、立项、排序和排期分别记录，进入池不代表承诺实现。

## 进入任务

先读原始反馈、问题或研究结论，以及已有需求池、决定和进度记录，明确是新增、清理还是更新。可从一条材料进入，不强制先完成其他 Skill；已有池时保留其维护源、编号、字段和有效内容，不另建冲突副本。

区分原始表达、研究结论、方案提案和实际进展。功能名不足以定义需求；问题或重要性不清时保留提案，只追问会改变判断的缺口，不把提出方或来源类别当作需求成立的证明。

## 从结论到候选动作

沿用课件：用户是谁 → 需求是什么 → 什么场景 → 遇到什么问题 → 推出动作。保留输入中指定的方案，分清用户提出与 AI 推导；一个问题可以有多个动作，动作不等于已经验证的解决方案。

检查候选能否说明重要性：关联什么用户问题、希望改变什么结果、有何依据。允许有依据的定性影响，不要求数值收益；缺失规模、频次或代价时留未知，不编造数据或评分。重要性说不清时保留候选与补证据建议，不伪装正式入池决定。

动作先进池、不排序；本项不打优先级分、定 MVP 或承诺本版实现。AI 产品需求围绕实际任务与问题，不默认每项都要加模型、Agent 或指定技术。

## 重复、字段与状态

比较新旧条目的对象、场景、问题和动作。名称相似不等于重复，同一问题的不同解法不自动合并；展示合并建议的共同点、差异与原有来源，由用户确定，已确定决定直接复用。

沿用六项主字段：能力项名称、业务痛点和目标、建设方向、需求来源、当前状态、需求描述。建设方向为增长、转化、留存、体验；需求来源为业务提需、产品自驱。分类不替代提出方和真实材料出处，不适配或依据不清时标待确定。

记录时按[需求池输出说明](references/requirements-pool.md)裁剪内容。描述或 PRD 只链接真实文档，未形成时如实记录；预计上线仅填已确定的计划，编号沿用现有规则，不为字段齐全造日期、链接或空 PRD。

课件状态包括立项、调研、设计、开发、测试、已上线、迭代、下线。依据实际资料或项目既有口径记当前状态，不要求单向经过全部状态；口径不同则说明对应关系。状态未知标待核实，不用“调研”代替未知，不将暂不处理记为下线。

新登记不等于立项通过，设计文档存在不等于开发完成，计划上线不等于已上线。保留仍有效的编号、原始来源和问题，说明本次更新内容与依据，不无声删除旧记录、改写原反馈或代替执行方的验收、上线、下线决定。

## 确认与写入

展示候选条目、重要性、拟合并或更新内容及关键未定项，由用户确定入池、合并与相关判断。已有明确决定、授权和可靠进展资料直接复用，不重新批准相同内容。

确定后在实际维护源新增或更新；用户明确要求先整理材料时，可写标明未知与未确认判断的草稿。仅讨论时不写文件。保存位置沿用用户指定或既有项目文档，对外工具写入按具体授权对象与影响执行，不因加载 Skill 扩大权限。

分别报告新增、更新、候选与待核实项，保留证据和决定状态；不把字段完整写成需求或效果已经验证。

## 完成与衔接

动作能回查用户、场景、问题与来源，入池理由说得清重要性；主字段有真实内容或明确未知，状态与链接有依据，合并保留差异和出处。

问题不清时可回到问题定义，证据不足时可补用户研究；本项不重选目标人群。需求记录供优先级与版本范围、立项和 PRD 使用，不自动展开后续流程。本项不做原型、代码、模型选型、评测或上线；后续 Skill 未接入时不声称已调用。

复杂需求变更协同、工具字段配置与通用合并规则缺少课件方法时，明确缺口，不自行增加固定审批制度。

## 方法来源

需要核对来源时读[课件方法索引](references/course-methods.md)。保留通用动作拆分、六字段、重要性门槛与状态参考；业务案例的名称、原话、数字、日期和方案不进入此 Skill。
